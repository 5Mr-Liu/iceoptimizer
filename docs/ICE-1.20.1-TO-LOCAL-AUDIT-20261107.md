# ICE 1.20.1 至本地测试包：功能与性能审查

审查日期：2026-11-07。用户反馈：本地测试未新增崩溃，但比其使用的 1.20.1 明显卡顿。

## 已知错误和可以核实的性能问题

### 1. 地形接口缺失后仍强制使用：尚未修复的崩溃缺陷

此前报告 UcObiXi 已出现 `RenderGlobal cannot be cast to TerrainVisibilityAccessor`。当前 `NativeTerrainPauseLifecycle.java:21`、`:43` 仍直接转换。`ClientOptimizerRuntime.java:73` 按选中的地形模式创建生命周期对象；`IceOptimizerTransformer.java:71` 起则允许某个补丁失败后保留原字节码继续运行。存在“补丁没装上，依赖补丁的运行逻辑还在使用”的路径。

这是已知兼容性缺陷；本次没有崩溃不能证明该路径已修好，也不能把它当作持续卡顿的证据。最终仍须看发生问题的启动日志，查明接口补丁为何没有生效。不能只吞掉异常，否则可能留下部分接管的渲染状态。

### 2. 等大小网格替换也会扩大分配需求：新增性能风险，分配差异已复现

发布 1.20.1 的 `NativeTerrainRenderer.store` 先释放旧区间，再申请新区间。当前 `NativeTerrainRenderer.java:90` 先上传新网格，`:107` 才释放旧网格。这是为了上传失败时保留旧网格，但代价是新旧网格短暂并存，而且同尺寸重建也不能直接使用仍被旧网格占用的空间。

独立探针使用实际分配器，替换一个 65,532 顶点的网格：旧顺序最高需求 65,532，新顺序最高需求 131,064；假设已有容量为 65,536，旧顺序可复用，新顺序需要增长。这里复现的是地址需求，未调用 GPU，也不是游戏耗时测量。

GL43 后端增长会执行 `NativeTerrainStorage.java:31` 的新存储分配，并在 `:43` 复制旧存储的已写范围。这个增长/复制机制原来已经存在，新增变化使它可能在更多替换场景触发。释放区间后存储容量也不会立即缩回。

建议：把该改动列为持续加载区块、频繁重建时的首要对照对象。保留完整发布/失败清理语义，评估更有界的替换空间或独立回退；不要把“旧网格保护”简单删除后宣称正确性完全不变。

### 3. 多重纹理会放大提交与索引复制次数：条件性开销，尚未证明是本次根因

AF/AA 使 G5 进入多重纹理模式时，`NativeTerrainMaterials` 为材质段创建记录，`NativeTerrainRenderer.java:287` 按材质段生成索引复制和绘制记录，`:289` 每次该网格重建索引还分配一个 `int[]`。`NativeTerrainGl43.java:103` 只能合并相邻同纹理记录，纹理变化时重新绑定并发出一批绘制。

这会把单图集下每层的集中提交拆为更多批次；材质段越碎，CPU 记录、GL 复制调用和绘制批次越多。材质捕获主要发生在区块准备阶段，不能误写成每帧都重新捕获所有材质。数组分配也发生在材质索引更新时，并非每网格每帧必定分配。

建议：未使用 AF/AA 的精简版可移除这一整套可选兼容功能；需要 AF/AA 时应保留正确材质路径，先优化批次和临时对象，不能只删贴图排序或 F6 支持。原 G5 的 VBO 限制也要一起处理，不能简单去掉材质代码却继续强行启用 VBO。

### 4. 差量同步的节省判断没有覆盖完整协议成本：可复现的收益判定缺口

`TrinketsDeltaSession.java:37` 每包新增 45 字节头；`:195`、`:199` 的选择条件仅要求差量体相对原消息节约超过 16 字节。首次发送或差量收益不足时也会使用带新头的全量表示。因此相对于原通道，不保证单包减少。

本次调用实际 Sender/Receiver：原消息 200 字节，变更连续 145 字节后，差量体 162 字节，被判为差量；连同头部总计 207 字节。解码还原完全一致。这证明的是传输格式开销，数字不包含 Minecraft 连接压缩及公共网络封装，也不代表真实饰品包分布。

建议：从默认性能配置移出，改为需要节省远程带宽时选用。要保留则应按完整线上成本与原协议比较，同时正确维护差量基线；不能直接跳过发送任意一包。

### 5. 差量同步新增复制、基线缓存和计算：已有测量支持的取舍

发送仍先执行原消息编码，再复制载荷、生成差量并为每连接保留基线；接收恢复后仍执行原解码及装备回调。它不减少这些原操作。`TrinketsDeltaSession.java:90`、`:131`、`:215` 可见复制；`TrinketsSyncBridge.java:103` 在连接锁内执行发送准备。

历史合成探针记录两端合计额外分配约 9.18–23.84 KB/包，额外算法时间随输入变化；每端每连接最多保存 64 条、2 MiB 有效载荷，临时分配不含在这个缓存额度内。以上不能直接换算为游戏 FPS。

关键排除条件：`TrinketsSyncBridge.java:54` 对单人 LocalChannel 直接走原协议；远程对端未声明支持也不进行差量。这种环境下不能把差量算法指认为卡顿根因。局域网远程玩家连接不等同单人本地连接。

### 6. 新 Capability NBT 比较在部分小对象上增加分配：已有历史探针证据

新增 `CapabilityNbtBridge` 在 NormalTagMap 下复用已有深度比较算法。记录显示某个小 NBT 夹具每次分配 656 → 1,088 B，增加 432 B，同时 CPU 耗时有所下降。这是 CPU 与分配的取舍，不能称为全面减少 GC；真实效果取决于大小分布和调用频率。

建议：针对小 NBT 重新决定是否值得使用该接入，或先从精简版移出新增 Capability 比较补丁。它沿用旧 `vanillaEquipmentNbt` 开关，关闭这个总开关还会关闭 1.20.1 已有的装备 NBT 优化，不是精确回退这次新增功能。

### 7. 空 VBO 空指针：已修复，应该保留

当前 `NativeTerrainPauseLifecycle.java:62` 已跳过空缓冲区。这对应第一份崩溃报告，是必要防护。不要为了精简退回没有判空的版本。

## 不应误归类为这次新增的内容

自有地形渲染器、F6 重建、GPU 存储扩容、原透明面坐标修复、原光影支持、旧装备 NBT 优化、保存调度和许多 OTG/实体优化已经在 1.20.1 或更早存在。

尤其是“约 2ms 区块上传时间片”原本也不覆盖所有渲染帧准备、GPU 等待与世界生成工作。当前仍在帧准备时生成变化网格的索引，但不能把这项既有机制全部列为新增问题。

通用 NBT 深复制实验已撤出，未进入本次交付包；若干世界生成/实体重构文档只是计划，不能算已实现功能，也无需为本次性能回退去删除它们。

## 推荐的精简次序

1. 以实际使用顺畅的 1.20.1 JAR 对应源码为对照；若只使用发布基线，应明确这一差别。保留必要崩溃与世界生命周期修复。
2. 单独对照新网格分配/发布策略；这是所有新地形路径都会经过的变化，比移除未被使用的 GL2.1 代码更有定位价值。
3. 按 AF/AA 实际状态决定是否需要多重纹理。需要保持同画质比较时，不能拿关闭 AF 的结果直接声称代码优化收益。
4. 默认移出 Trinkets 差量协议、低收益标量复用和小 NBT 增分配的新增接入。单人测试不把关闭差量协议的结果当作首要验证。
5. 后续逐组保留/加回 QualityTools、RC 清理、Lycanites 单次解析、已知 Capability 快路径、索引复制及命令部分上传；每次只改变一组，比较同设置同路线的最长帧及 P95/P99，而不只看平均 FPS。

这是下一轮取舍建议，不是已执行的修复或性能结论。历史自动测试能验证覆盖到的语义，不能替代用户已经报告的实机卡顿。
