ICE：持续游玩性能与渲染算法改造方案
日期：2026-10-11
基线：当前工作区 ICE 1.0.27；Minecraft 1.12.2 / Forge / Java 8 / LWJGL 2。
状态：用户已授权持续实施；1.0.27 源码、编译类和发行包已冻结，1.0.28 开发中。
目标：代表性已加载区域正常游玩的原生 FPS 几何平均相对冻结的 1.0.27 提升至少 50%，
      各场景 P95/P99 慢帧不恶化，同时报告相对无 ICE 的结果。50% 是实测验收目标，
      不是预测或保证；局部排序/HUD/模型微基准不能代替整帧收益。

一、判断与边界

需要深入修改，但不能把当前整个适配层判成负优化。1.0.27 已证明部分地形提交和长文本绘制
有局部收益；整包端到端收益还未验证。现有实现并不缺 Arena、方向剔除、软件遮挡、模型
palette、字体缓存等组件，下一步应改进数据流、接管范围和重复工作的发生频率。

旧文档 ICE-MODERN-OPENGL-RENDERER-COMPLETE-DESIGN.md 中的翻倍预算来自旧场景推算，
不能用作 1.0.27 的实测结论。本方案不承诺翻倍，也不把 CPU 栈采样占比乘整帧时间当成
子系统的精确耗时。CPU、GPU、驱动和显示是重叠流水，应分别量出关键路径。

默认保持画质、分辨率、视距、实体距离、粒子数量、动画频率与游戏逻辑；不跳 Tick，
不把预生成、插帧或 HUD 降频作为本方案的性能成果。第一交付目标是当前无 ShaderPack
的兼容环境；有 ShaderPack 时继续原路径，之后按程序与 pass 分别验证。未知渲染器继续
执行原实现，不能为了扩大覆盖率跳过回调、猜测状态或隐藏不确定可见物。

二、当前证据及取舍

1. LwjglTerrainArena.java:1298 的 drawDirectionalRanges 已共享 region 变换、过滤面方向、
   合并连续范围。1.0.27 原生离线测试：纯 Arena 约 0.59 ms，对照原提交约 0.70–0.73 ms；
   混合外部 VBO 约 0.66 ms，对照约 0.71–0.74 ms。保留这条默认路径。
   不恢复 1.0.26 的跨页 shader/bindless/GPU command 默认路径。

2. PrimitiveTerrainVisibilityBridge 已有无装箱 BFS；CurrentFrameTerrainOcclusion 已在
   编译期捕获遮挡网格、使用当前相机保守栅格，并在 filter 中堆排序近远候选。
   不能再把“新增 primitive BFS 或软件遮挡”作为新收益。改进点是区域层次、候选组织
   和重复计算；堆排序与栅格的净收益尚需分开量，不能仅凭存在排序就定为负优化。

3. ChunkPrimitiveSortBridge.java 已有小批稳定归并、大批四趟基数排序及恒定位跳过。
   大批次已经是 O(Q)，新方案不能虚构 O(Q log Q) -> O(Q) 的提升。
   目前 sortValidated 仍先复制完整顶点块，再按 quad 顺序写回。这是可具体改变的数据流。

4. HudRenderBridge.java:150 在 Forge 事件前 flush，事件照常执行并使状态镜像失效。
   已有字体布局缓存与动态流，尚不能等同于整套 HUD 的计算与绘制缓存。
   1.0.27 的 128 字形批次约 4 us，原路径约 9 us；1–4 字形仍多约 0.2–0.3 us。
   这些量不包含整个 HUD 逻辑、Forge 监听器和所有模组图标，不能外推整体 FPS。

5. LwjglModelPoseBatch.java:100 已经做多部件 palette，begin 会读取模型视图矩阵，
   在状态未知时补采样，并查找匹配网格形状。新方案重点是让已知模组在更高层导出模型
   数据，减少逐 GL 调用适配；不是再写一套同名 palette。单件 Display List 回退保留。

6. ModernRendererRuntime 的地形路径仍关联后端状态、采样和计数；CorrelatedRenderProfiler
   的 beginCpu 会创建 key/scope。它们是存在的成本，不是已证实的整局主因。
   应让未录制时走轻量入口，并直接测量录制开关的差值，不能用重型监控补偿重型优化。

7. SpriteVisibilityTracker 已有有界可见纹理追踪、不可变像素副本和补传逻辑；
   粒子和模型也已有实例化/缓存实现。保留有效机制，扩大适配前先查实际命中和总成本。
   当前 mods 已有 EntityCulling 和 particleculling，不另加重复的实体遮挡系统。

继续保留：NBT 单遍比较、碰撞与寻路工作区、最近目标线性选择、按需 OTG 缓存、
BO3/BO4 执行优化、AO/矩阵工作区、纹理参数去重、资源预算和安全退休。
继续停用：注册时全量预读、不能合批的逐件 VAO 替换、已测慢的旧地形 GPU 提交路径。

三、整体架构：复用现有组件，提前整理稳定数据

资源/网格/模型变化时：
  解析实际依赖 -> 整理不可变数据和固定操作 -> 发布带版本号的数据
每帧/每个视图：
  读取本帧输入 -> 更新变化部分 -> 筛选可见工作 -> 按原顺序提交
外部事件/未知 GL/未知模型边界：
  完成当前提交 -> 执行原回调 -> 标记状态未知 -> 下一个已知范围重新建立状态

继续使用现有 FrameCoordinator、PassGraph、资源账本和 generation，不新套一层全局框架。
后端选择在配置、资源、上下文和帧边界发布。一个 region/layer 的几何只允许一个后端
持有并绘制。禁止同一批地形同时走 ICE、Nothirium 和 Celeritas。

已知数据可使用紧凑原始类型数组，避免把每个顶点/部件再包装成一串命令对象。
缓存键必须包含实际依赖的 world/resource/atlas/context/model/mesh/state 版本。
“版本没变”只有在所有修改入口可追踪时才成立；未知可变数据必须重读或退回原实现。
渲染线程负责 GL。Worker 只处理线程安全快照，保持原有线程安全限制。

四、地形：三个确定的研发方向，一个有条件的候选

A. 区域层次筛选 + 变化驱动的元数据

在已有 section 网格上增加轻量区域目录，保存子 section 范围、非空层掩码、包围盒、
网格版本和缓冲区句柄；在区块加载、卸载或重建完成时更新。继承现有 region 划分，
避免额外复制整套网格。每个视图先测试 region，再测试相交的 section。

同一视图内共享只读的候选 ID 和已验证元数据，各层仍生成自己的合法顺序。
相机、投影、FOV、门户/阴影视图变化必须重新作相应可见性判断；不能因为世界未变就
复用上一帧隐藏列表。只复用与视点无关的拓扑和版本一致的静态信息。

成本模型：更新元数据约 O(D)，每视图约 O(R + C)，D 为变化 section 数，R 为区域数，
C 为通过区域粗筛的 section 数；最坏仍为 O(N)。开阔场景可能收益很少，额外目录
读取也可能变慢，应在开阔、室内和混合所有权三类场景分别验收。

B. 遮挡工作线性组织，保持当前帧保守判定

候选实验：将 CurrentFrameTerrainOcclusion 的逐项堆取近远，替换为预分配的粗深度桶，
如 16/32 桶，桶内保留原候选顺序；只改变遮挡处理顺序，最终绘制仍按原列表顺序压缩。
分桶与遍历成本 O(C + B)。粗顺序可能降低遮挡效率，必须同时量被省掉的 GPU 工作，
不能仅比较 CPU 排序时间。保留旧算法作为对照，不预先认定新桶数或分桶算法必胜。

遮挡源只取确定不透明且覆盖可证明的真实几何；遮挡源向内保守，被测试范围向外保守。
近裁剪面、退化形状、动态方块、资源变化、未知纹理或预算耗尽一律视为可见。
当前帧的覆盖结果不能越过视图和资源版本使用。上一帧数据最多指导测试顺序，不能
单独作为剔除证据。避免 GPU 同步读回与额外深度 pass 成为正常游玩的固定成本。

研究参考：Masked Software Occlusion Culling 将深度与覆盖信息分开，支持层次判定。
Intel 参考库已归档；只把它作为算法/对照来源，不作为会自动提速的必装原生依赖。
第一阶段保留 Java 实现。如果完整 profile 证明软件栅格本身占明显成本，再试批量 JNI
的 SIMD 栅格，调用成本、数据复制和发布成本必须计入；不按一个候选一次 JNI 调用。

C. 透明层顶点常驻，只排序/上传索引

优先面向 ICE 完全持有、格式已验证的透明网格：
  1) 区块重建时发布原顶点流、quad 中心和原始排列；保留现有浮点求值次序。
  2) 原路径触发重排时，用相同距离键和相同稳定性规则计算顺序。
  3) 顶点保持不动，只更新 quad 的索引流；先使用兼容上下文 GL_QUADS 的索引绘制，
     不顺便更换三角化方式。材质、光照、纹理、法线和 draw 顺序保持。
  4) 使用索引页版本与非阻塞退休；无安全空间时按原排序路径完成当前重排，
     不能等待 GPU，也不能用旧顺序凑数。

对于每顶点 28 字节、每 quad 四顶点、32 位索引的已认证格式：
  原完整顶点重传：112 字节/quad。
  新索引重传：16 字节/quad。
只计算这部分重排上传，字节量理论上下降 85.7%；不是地形帧时间下降 85.7%。
第一次上传仍需完整顶点，常驻 EBO 会额外占内存。其它 stride 单独计算。

第一步可先给现有排序增加“键已经有序”的线性检查，跳过排序和整块复制。
后续保留上次排列时，须逐对验证本次距离键及本次原调用输入的平局顺序；
不能把初始 quad ID 永久当作所有重排调用的稳定性依据。重复坐标、NaN、正负零和
相同距离都沿用现有比较规则。大批基数排序本来是 O(Q)，主要收益来自少搬数据。

外部 VBO、未知格式、OptiFine 特殊顶点和需要读取可变 BufferBuilder 数据的消费者
继续现有路径；新的“只更新索引”不能悄悄改变它们观察到的顶点排列。
模型/mesh 版本变化使旧索引、中心缓存和顺序证明一起失效。

Sodium 透明排序研究提出静态排序、相机区域失效和分割树，适合进一步研究。
但其几何深度顺序可能与原距离排序的画面不同。严格等价版本不默认引入 BSP、
近似 OIT 或分割 quad；先完成相同顺序的索引数据流，再决定是否独立做画面改进项目。

D. 保留直接范围提交，按测量决定是否引入更大批次

1.0.27 direct-range 为默认。只有同一变换、同一页、同一状态的有序范围，才比较
逐范围 draw 与 glMultiDrawArrays；阈值由测试场景确定，并在配置/资源边界固定。
多范围构建与上传成本必须计入，不因 API 叫 multi-draw 就默认启用。
不恢复每层重建 offset/indirect 数组、逐顶点额外变换或额外 GPU 可见性 pass。
只有数据证明 CPU 提交是主要瓶颈时，才把驻留命令和更完整的 shader 后端列为候选。

五、HUD：按元素保留数据，按依赖变化更新

第一阶段采用明确元素适配，不缓存整个 Forge 事件结果。新增的主要数据是已知元素的
输入快照、依赖版本和不可变绘制数据；继续使用 FontLayoutCache 和现有绘制器。

元素处理规则：
  固定边框/背景：分辨率、GUI scale、资源或布局改变时重建。
  已知数字/文本：实际显示值、格式、语言、字体、颜色/样式变化时重建排版。
  血量/护甲/温度/耐力：每帧读取完整视觉输入，有变化同帧更新。
  血量闪烁/受伤反馈/准星/聊天淡出：时间与动画也是依赖；变化时继续每帧渲染。
  热栏物品/JEI/第三方 HUD：先按真实渲染器逐项认证，不能仅按 item ID/NBT 引用缓存；
    动态纹理、附魔、数量、耐久、模型覆盖和自定义 renderer 都可能影响结果。

先优化可证明纯计算的字符串格式、布局、图标选择和几何生成，随后才对昂贵、稳定且
有明确合成语义的连续片段尝试小范围 FBO 缓存。缓存命中依然在原顺序上绘制。
每帧触发的 Forge 事件次数、取消、顺序和副作用保持不变；只能替换已适配监听器中
经确认无副作用的计算/绘制部分，不能直接跳过整个监听器。

FBO 缓存需要单独验证混合方程、预乘 alpha、目标 alpha、sRGB、裁剪、Z、缩放和
纹理过滤。依赖目标颜色、特殊混合或未知 GL 状态的元素不能缓存到通用透明纹理。
多一遍离屏绘制和纹理合成本身有成本，小元素继续直接绘制。图像不一致就保留原路径。
正常模式不以跨帧轮流更新或固定 HUD 低 FPS 换性能，受伤信息不能晚一帧才出现。

1–4 字形入口应缩短到已解析文本的直接绘制路径，避免为微小批次建立完整采样/队列
状态；布局缓存仍可复用。大文本保留现有索引合批与持久页环，禁止为统一架构回滚收益。
推荐顺序：原版固定 HUD 与已知数字 -> Dregora 高频状态栏 -> 热栏/物品 -> 其它 GUI。

六、实体/TESR：从逐 GL 适配推进到已知模型数据适配

这是地形/HUD 首轮之后的主要研发方向，目标是已加载区域里的密集生物、战斗和基地。

A. 在模型加载/结构改变时，把已知模型拓扑、部件 ID、父子关系、材质边界、可见性
   条件和动画通道整理为数组。Lycanites 的 frame 类型和名称绑定优先移到资源阶段。
   Mo' Bends 已有拓扑/四元数缓存，复用并核查依赖完整性，不能再重复实现。

B. 每次实际姿态变化仍按原动画顺序计算；父矩阵乘局部矩阵的遍历用扁平拓扑执行。
   如果局部输入和父矩阵均未变，复用该子树的派生矩阵。矩阵原始位、可见部件和
   缩放规则需要完整比较。先争取同一次渲染里的派生结果复用，再扩展到主/阴影 pass。
   复用键要包含实体生命周期、tick、partialTicks、pose/model/装备版本及其它实际
   动画输入；仅用 entityId + tick 不正确。回调修改模型、世界或视图时必须失效。

C. 已知 adapter 直接给现有 ModelPoseBatch 提供矩阵 palette 与材质片段，减少
   多层 glRotate/glTranslate 拦截和每个小模型的状态重建。进入未知 GL 后仍需必要
   的状态重读，不能把删除 glGet 查询当成可无条件做的优化。
   每个实体先按材质片段合批，保留非合批 Display List。矩阵 palette、普通模型和
   固定管线光照的等价性都要验证，不能仅看 draw-call 数量下降。

D. 跨实体实例化仅作为后续候选，条件为同网格/材质/渲染状态、透明顺序允许，且
   事件监听器看不到提交时序差异。默认不跨 RenderLiving Pre/Post 或模组 layer 回调
   延迟绘制。无法证明这些条件时，每实体材质内合批就是合法边界。

E. 继续尊重现有 EntityCulling/视锥判定。仅能跳过确定无副作用的不可见视觉工作；
   不因为模型不可见就停止实体 AI、动画状态推进或 Forge 回调。发光、阴影、轮廓、
   名称牌、牵引线、超出本体包围盒的部件按各自视图和完整范围处理。
   TESR 只对已知静态网格与动态参数做分离，不做通用的“静态方块实体全部缓存”。

适配顺序：用实际战斗/基地数据选择成本最高的模型；候选为 Lycanites、SRP、Mo' Bends。
按耗时覆盖率排序，不按模型数量排序。新路径命中但总耗时更高同样判为失败。

七、辅助路径与框架自身成本

粒子：复用已实现的 billboard/FBP 流，仅在认证的状态片段内合批；透明顺序、RNG、
碰撞和寿命保持。小批继续原路径，大批比较实例数据准备、上传、draw 与 GPU 总成本。
纹理：保留当前可见性证据和补传机制，验证所有消费者；无法完整追踪就按原频率更新。
当前帧首次可见前须具备正确动画帧，不准以一帧旧纹理换低上传量。PBO 只保留实测
获益的大小区间，不为了“异步”再增加整块 CPU 拷贝。

框架：未启用诊断时，不创建每段的 profiler key/scope，不组织完整场景指纹，不做
频繁在线 A/B；后端可用性与安全检查保留。资源/上下文变化、配置变化仍触发必要验证。
已验证后端正常执行稳定的短入口；诊断模式才开启细分 CPU/GPU 采样和详细原因计数。
渲染线程计数使用预分配数组，低频发布不可变快照；跨线程数据保持正确发布与所有权。
Runtime 中条件分支只做源码存在性记录，是否值得改由禁用诊断的对照决定。

不把工作拆到更多线程当作必然收益。新增 Worker 必须基于现有线程池和有界队列，
合并同 section 的重复重建、淘汰过期任务；最终发布校验版本，防止旧结果覆盖新状态。
这些任务策略用于减少游玩中的重建尖峰，不计作静止场景直接增帧证据。

如果慢帧主要来自同进程服务器的实体逻辑，渲染改造不能代替它的优化。该分支保留
现有碰撞/寻路改进，继续针对重复候选扫描和目标筛选做算法审查：复用原有空间分区，
保留候选顺序、可变状态读取和回调次数；不另堆一套每 tick 全量维护的索引，也不跨
可能修改世界的回调复用旧查询结果。只对实际命中的热点单独设计并做行为对照，
不能把线程数增加、远处实体降频或压低刷怪量混入本方案的等价收益。

所有候选都计算完整成本：缓存命中检查、变化检测、队列/拷贝、状态恢复、CPU 提交、
GPU 执行与额外内存；省掉的旧工作必须大于这些新成本。若最慢的一段仍未改善，
其它段局部变快可能不会增加吞吐，应如实记录。

八、成熟后端与自研的关系

地形设置三种互斥候选：ICE 1.0.27 范围提交、改进后的 ICE、外部成熟渲染后端。
Nothirium 和 Celeritas 分别建立独立测试配置。GTNewHorizons/Celeritas 的 nh-main
README 声明支持 Forge 1.12.2 + Java 8 + LWJGL 2；Cleanroom 文档描述的是另一条
运行环境路线，两者不能混为一个版本的安装要求。

候选渲染器不是“装上就算适配完成”。冻结准确源版本、依赖和构建结果，检查当前
OptiFine G5、RenderLib、RLFoliage、实体渲染与纹理行为。Nothirium 作者列有 OptiFine
Smart Animations/custom block render layers 等限制。会迫使画质或功能变化的组合
不得混入等画质性能结果；有特殊功能需求的场景继续兼容路径。

复用第三方代码前核对具体提交和文件许可证；Sodium 新旧版本许可证有变化，不能
因为旧分支开源就直接拷贝最新实现。论文算法可以独立实现，但源码复用仍遵守许可。

决策：外部后端在等功能、等画质、同场景下稳定胜过 ICE，则使用它负责地形，ICE
保留实体/HUD/逻辑优化；反之保留 ICE。不要为了保留自研身份维护一个实测更慢的后端。
本方案不要求先迁移 Java 或开发外部 EXE；可选 JNI 库也只处理已经证实值得搬走的纯计算。

九、实施顺序、交付物和退出条件

第 0 步：冻结 1.0.27、无 ICE 对照、已加载区域的场景副本和准确配置。
把性能预算按实际 CPU/GPU 关键路径重新建立；这只是实施前置，不把采集工具作为成果。
交付：可重现基线和每条候选的成本清单。旧会话与旧版本比例只能作定位线索。

第 1 步：地形透明索引数据流 + 已排序快速通过；HUD 已知元素的依赖驱动布局复用。
这是首轮主交付。小字体入口和未录制时的轻量诊断入口随相关修改分别对照。
交付：独立开关、逐像素/事件测试、透明层和复杂 HUD 的真实游玩结果。

第 2 步：地形区域目录、候选共享、粗深度桶与现有遮挡算法逐项竞争。
可同时准备成熟后端对照，但不与新 ICE 地形叠加。每项只改变一个主要因素。
交付：开阔/室内/水面/混合外部 VBO 对照；不只报告剔除比例和提交次数。

第 3 步：已知高耗时实体的编译模型数据、派生姿态复用和每实体材质合批。
交付：密集生物/真实战斗/装备变化/受伤/视角变化等场景的等价性与帧时间。

第 4 步：依据剩余成本决定 FBO HUD 缓存、粒子、纹理、原生 SIMD 或更完整后端替换。
这些是条件候选，不为方案看起来完整而全部默认安装。ShaderPack 适配独立验收。

每一步保持一个可直接回退的完整版本。子系统不通过等价性则不开启；只有微基准
变快、整局没有净收益的候选不进入默认路径。若 HUD 总成本已很低，则停止继续投入
HUD 并转向实体/地形关键路径，不能坚持低价值顺序。

十、验证方案：最终看原生 FPS 与慢帧

三方主对照：
  A：同整合包、移除 ICE Optimizer；其它模组与设置不变。
  B：冻结的 ICE 1.0.27。
  C：本方案候选版本。
1.0.26 只保留为历史退化参考；外部成熟后端单独作 D 对照。比较地形后端时其它
有效 ICE 模块保持一致。F6 暂停会保留启动补丁和已有缓存，不能代替 A。

核心场景全部位于已加载范围：
  1) 固定站位观看复杂建筑/植被，并持续转视角。
  2) 室内与遮挡密集基地，含可见 TESR。
  3) 固定生成规则的密集实体与战斗，保留真实 AI/攻击/受伤。
  4) 水体、玻璃、透明交叠和边界角度变化。
  5) 复杂 HUD、热栏、状态变化和 GUI 操作。
另测低负载场景防止额外框架开销。跑图和冷加载单列，不混入持续游玩得分。

各配置从同一可恢复存档快照启动；固定分辨率/画质/视距/VSync/限帧/电源条件。
先等待 JIT、纹理和区块准备稳定。轮换 A/B/C 顺序，例如 ABC、BCA、CAB，再重复；
每配置至少 5 次独立有效运行，每次 60–120 秒。随机实体行为无法做到逐帧完全重复时，
记录场景条件和差异，使用多轮分布；不能只挑一个视角截图或最高 FPS。

性能运行与重型图像验证分开。正式性能结果用相同低开销采集，并另作采集关闭的
外部帧时间复核；GPU query 延迟回收，真实游玩测量不插入 glFinish/同步读回。
按视图关联 CPU 与 GPU 数据，不能把 GPU 计时和 CPU 提交时间直接相加当整帧。

记录：原生呈现吞吐、帧时间 P50/P95/P99、每分钟超过 16.7/33.3/50 ms 的帧数、
CPU 阶段/GPU pass、服务器 MSPT、GC、分配、Native/RAM/VRAM 与缓存淘汰。
分别报告每次运行及汇总，置信区间以独立运行或时间块为单位，不把相关的逐帧样本
假装成数万个独立实验；小于测量噪声的差异归为无明确收益。

正确性覆盖：玻璃/水面顺序、草叶孔洞、近裁剪面、相机穿越、资源重载、FOV/GUI scale、
维度/上下文切换、原始 GL 插入、Forge 取消/异常/副作用、实体部件显隐/装备/受伤、
HUD 闪烁与即时反馈。受控输入下图像应与基线一致；出现浮点/合成差异不能自动当成
“视觉差不多”通过，先定位并保留基线。故障注入继续覆盖预算耗尽和上传失败，
已提交内容不重复重放，未提交内容准确回退。

建议立项验收目标（目标，不是预测）：代表性已加载场景原生 FPS 几何平均相对 B
提升至少 50%（用户后续指定的目标），且逐场景 P95/P99 无超出重复测试噪声的退化；
还要明确报告相对 A。按持续实施推进，无需按阶段重新请求许可。
不达目标就报告实际值与失败原因，不能以测试数量、GL 调用减少或局部倍率代替成果。
组件是否保留依据净收益与维护成本；即使总目标达到，也不把无收益候选一起打包。
