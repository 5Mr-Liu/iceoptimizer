ICE 1.0.30 Build16 — F6 chunk-upload deadlock fix
2026-10-13

Build15 is superseded. A user reported an indefinite freeze when pressing F6.
The original game was inspected read-only: the installed optimizer hash matched
the released Build15. Its client stopped before the switch-completed log; the
integrated server continued and client network actions eventually overflowed.
No surviving user JVM was available for a live thread dump.

Reproduction and cause
----------------------
The Build15 release smoke called setRuntimePaused directly at ClientTick.END,
after a 60-second warmup. It did not validate the actual key handler while
chunks were being rebuilt. A new test fixture sends KeyBinding.onTick(F6),
letting the production ClientOptimizerController process the request normally
at ClientTick.START. A first ordinary key test completed; tick phase alone is
not the cause.

The stress fixture marks the 15376 render sections dirty, allows three client
ticks to start asynchronous builds, then sends F6. Six alternating switches are
requested, using 2-second scenes and the existing 5-second settling interval.
These measurements are diagnostic only, not an FPS comparison or performance
acceptance test. No test-specific delay or bytecode instrumentation is used.

Build15 stress run reproduced the indefinite wait on the fourth switch, from
paused to enabled, at 20:20:37 local time. At 20:21 the Client thread was still
parked in ArrayBlockingQueue.take -> ChunkRenderDispatcher.allocateRenderBuilder
-> stopChunkUpdates -> RenderGlobal.ice$stopChunkUpdates ->
NativeTerrainPauseLifecycle.beforeChange -> setRuntimePaused -> F6 handler.
Stack: build/fps-target/130-build15-f6-key-stress-hang-jstack.txt.
Snapshot: C:/Users/32884/.codex/scratch/ice-fps-target/live-130-build15-f6-key-stress
Only this identified isolated JVM was terminated after collecting the dump.

stopChunkUpdates clears queued builds, drains the currently queued uploads,
then blocks until it can take every render builder. A task still compiling can
queue its upload AFTER that drain. Its builder is returned by the upload
completion callback, which needs the now-blocked client thread. The worker
itself can already be idle waiting for a new build; the outstanding upload
future retains the missing builder. This is an unbounded wait, not slow GL
resource deletion and not a request to wait longer.

Fix
---
Cancel every RenderChunk's existing compile task before calling the blocking
dispatcher drain. This mirrors the ordering of the incoming loadRenderers,
which cancels tasks through ViewFrustum.deleteGlResources before draining.
Cancellation marks compiling tasks finished and cancels pending upload futures,
so their completion callbacks return builders without requiring client uploads.
GPU geometry is still released/rebuilt only after draining and switching mode.
No configuration, quality or selected optimization is silently changed.
Add one switch-request log before handoff, so future incomplete requests can
be distinguished from completed switches without a permanent HUD.

Limits
------
Switching still rebuilds terrain and can cause a finite loading hitch. This fix
removes the demonstrated circular wait; it is not a promise of zero pause or
zero chunk-loading time. Default-on, all configured runtime modules including
native terrain, and restore-previous-configuration behavior remain intact.
The separate profiler and the original game files have not been changed.
Build12/Build13 experiments remain rejected; formal performance status is unchanged.
