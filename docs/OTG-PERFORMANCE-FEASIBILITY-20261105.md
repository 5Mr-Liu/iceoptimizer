# OTG 全面性能优化可行性调查

调查日期：2026-11-05。目标：减少游玩中的长停顿、提高新区块生成速度、降低服务端每 tick 耗时，并评估客户端帧耗时。本文是源码和现有证据调查，没有替换游戏 JAR，没有新的实机收益测量。

## 结论

直接修改 OTG 可行，值得做一个以现用 v9.7 为兼容基线的优化分支。优先做结构选址、未加载地形查询、图片生物群系和方块放置路径的算法改进，再考虑受控并行。把 ASM 补丁改成源码本身通常不会自动变快，收益来自减少实际执行的工作。

OTG 优化最可能改善探索、传送、结构密集区域和保存时的卡顿。它也有客户端雾效、服务端刷怪等常驻逻辑，所以作用不局限于生成新地形；但它不能代替 ICE 对 OpenGL 帧提交、网格上传和 GPU 等待的优化。单机中服务端与客户端共享 CPU、内存带宽及 JVM，服务端生成降耗可能间接改善帧时间；专用服务器上的 OTG 优化主要改善 TPS 和区块供应。

## OTG 目前怎样运行

```text
区块请求 → OTGChunkGenerator.generateChunk → ChunkProviderOTG.generate
                                  ↓
                    生物群系 / 噪声 / 地表 / 洞穴 / 结构准备
区块填充 → ObjectSpawner.populate → BO3/BO4、资源、方块与实体放置
世界保存 → CustomStructureCache → 结构序列化 / 压缩 / 文件写入
服务器 tick → 传送检测、每秒刷怪/粒子周期、模组数据消息
客户端渲染事件 → 雾颜色和雾距离计算
```

它是“生命周期/事件回调 + 同步计算”的组合。Forge 触发事件，不意味着处理会异步或自动分摊。生成器入口由 Minecraft 请求区块时调用；耗时的回调仍然会阻塞调用线程。仅改成“事件驱动”不能解决计算和 I/O 尖峰。

## 已有优化不能再次计入收益

| 来源 | 已覆盖内容 | 对后续方案的影响 |
|---|---|---|
| OTG v9.7 | ArraysCache、biome 数组生成、BiomeGroup、坐标哈希及 FIFO 等改进 | 网上针对旧版的建议可能已经过时 |
| ICE | BO3 数组执行、BO4 列偏移与布局复用、解析、同步配置/NBT 缓存、结构保存分配与压缩 scratch | 源码迁移须与这些模块逐项去重 |
| ICE `OtgColumnQueryAdapter` | 修复列缓存键、写错缓存值及生命周期；已加载可变区块不复用旧列 | “修复列缓存”不是本次新增收益，下一步是避免不需要的整列构造 |
| RLTweaker 配置 | OTG 方块快照问题、实体名称转换、附近结构检查 | 不应再次把这些算为未解决热点 |
| FermiumMixins 配置 | 大地图结构缓存加载、禁用自带预生成器、保存/填充协调等 | 不能直接根据原始 OTG 的忙等代码认定当前正在忙等 |
| EagleMixins 配置 | 部分 BO3 BlockFunction 缓存、MaterialSet 检查等 | 材料检查和 BO3 改动需要以补丁生效后的路径为基线 |

ICE 的 `OtgObjectPreparationBridge.prepare` 当前是保留接口的空实现，实际加载按需进入缓存；不能根据模块显示名误以为正在后台预读所有结构。

## 优先优化方案

以下优先级是结合代码和预设给出的工程判断。每个方向均需在现有整合包基础上测净收益。

### 1. 未加载区块的单点/高度查询：优先级 P1，可行性高

v9.7 的 `getMaterialInUnloadedChunk` 为取一个方块先取得 256 格整列；`getHighestBlockYInUnloadedChunk` 也先取得整列再从高处扫描。ICE 的缓存减少重复列构造，但冷列或已加载可变区块仍有这部分工作。

建议分开实现单点、最高符合条件方块、完整列三个入口。单点直接读取目标 chunk section；高度查询自上而下访问 section，跳过不存在的 section，遇到符合原条件的方块立即返回。完整列只在调用者确实需要时生成。复用原始地形预览区块，并保持加载、填充及失效规则。

上游新分支已有直接访问实现可供参考。回移时保留旧版 solid/liquid/snow 判定及模组方块行为，不能顺手使用新版材料语义。比较同列反复查询和大量不同列查询两种负载，防止更快的单点路径导致重复查找增加。

### 2. BO4 选址距离查询：优先级 P1，可行性高

`CustomStructurePlotter.isBO4AllowedToSpawnAtByFrequency` 对同类型已生成结构列表、同组结构映射做遍历，并逐个计算距离。随着记录积累，某些查询的成本会增长。调查时新上游仍保留了这些扫描。

建议增加按空间划分的索引，筛选可能影响当前候选位置的结构，再用原始距离条件精确判定。按名称与组维护索引，世界加载时重建，新增结构时同步更新；第一次实现保留原存档格式。组的判定半径取双方半径较大值，因此不能只查询候选自身半径，应采用覆盖半径的索引或保守上界。

优先减少候选数，而非仅替换 `Math.sqrt`。原逻辑包含 `floor(sqrt(...)) <= radius`，直接改成平方距离 `<= radius²` 会改变边界。保持原判定也可避免溢出、舍入差异。此处是纯布尔存在查询，能够在不改变分支抽签顺序的前提下加速。

### 3. 图片生物群系避免无用后备生成：优先级 P1，需先验证覆盖率

当前预设恰好使用 `FromImage + ContinueNormal`。v9.7 的 `LayerFromImage.getInts` 在判断图片像素是否足够回答请求之前，先计算整片后备生物群系；如果请求全部落在图片内的有效像素，该结果会被全部覆盖。

建议为图片有效区域建立查询辅助信息：只有请求越界或涉及未定义像素时才调用后备层；完全有效的区域直接读取图片生物群系。混合区域第一阶段仍走原有完整后备计算，不急于拆成小请求。

这是待验证的优化候选。必须确认当前地图有效覆盖率，并验证跳过调用不会改变层的后续随机状态、ArraysCache 复用和其他模组注入的可见行为；比较本次和后续多区块请求序列。地图外探索几乎不会从这个快路径受益。

### 4. BO3/BO4 方块放置与材料检查：优先级 P1/P2，可行性中高

现有逐方块路径包含区块坐标构造、四项缓存匹配/锁、材料状态转换、方块设置、NBT 和通知。建议在一次结构执行上下文中复用当前区块/section、配置和材料查找结果；连续访问同一区块时走快路径，跨区块或重入时回退原有语义。

保持方块写入顺序、随机调用顺序、TileEntity、元数据、光照及通知。不能通过跳过通知、关掉光照或任意重排写入取得成绩。`MutableBlockPos` 只是一项小改动，且不能让可变坐标逃逸到外部代码。先测真实 `setBlock` 调用链，再决定是否值得改写批量放置层。

材料匹配优化应以已启用 EagleMixins 后的代码为基线。新版上游的材料重构还修改了语义，适合拆分评估，不适合整套复制。

### 5. 常驻刷怪、粒子和实体扫描：优先级 P2，可行性中高

原 `ServerTickHandler` 每秒为已加载 OTG 世界执行刷怪周期：枚举玩家周围区块、扫描实体、计算到玩家的距离，并把候选刷怪器逐个插入有序列表。候选多时，插入排序可能达到平方级工作量。

先把“逐个有序插入”改为收集后稳定排序，保留原始遍历顺序作为同距离时的次序，并复用临时存储。继续评估活动刷怪器索引和玩家区块变化驱动的候选集合更新；实体动态加入/移除、玩家传送、区块卸载必须更新索引。

不能直接降低刷怪频率或改变 RNG 消费。原周期还含实体消失处理，不能只以“没有刷怪器”为条件提前退出整个方法。该方向只有活动刷怪器/实体较多时才可能产生明显收益。

### 6. 启动、首次遇到结构与磁盘读取：优先级 P2

已有按需加载与缓存，因此重点应是当前冷加载的打开文件次数、重复配置实例化、NBT 解析、结构旋转/分支预处理，而非继续扩大缓存。可在源码中构造可复用的不可变结构模板；可变 NBT、一次生成的状态仍独立创建。

离线预编译/持久化模板缓存可作为第二步，键需包含格式、配置和依赖版本，并具备修改失效。不能在启动时无条件读取全部数万份对象，导致更长启动和无效 I/O。它主要改善首次使用的延迟，不等于提高已加载区域 FPS。

### 7. 保存、序列化与压缩：优先级 P2

OTG 已有 region `requiresSave`，不能再把“只保存脏 region”当作全新优化。ICE 也已减少一些分配、分组和压缩 scratch 开销。

剩余方向是测量并减少脏 region 内重复遍历、序列化复制和锁占用；如压缩仍占主线程显著时间，可由主线程生成不可变快照，交给有界工作队列压缩，按保存代次和原有顺序提交。异步方案需要保存完成屏障、失败反馈、退出/卸载等待、快照后再次变更的版本检查，成功写入后才能确认对应代次已保存。

这是存档生命周期改造，复杂度高于同步循环优化。不能直接在线程池中遍历正在变化的结构对象，也不能把 ICE 对原版区块保存的异步压缩误认为已经覆盖 OTG 结构文件。

### 8. 客户端雾效、颜色与配置查找：优先级 P3

`ClientFogHandler` 在颜色、距离事件中分别扫描邻域。可以评估将同一次回调中的配置表查找移出内层循环，以及同帧共享已认证的采样结果。跨帧缓存需处理世界、位置、区块/生物群系变化、配置、视距及动态天气/药水效果。

已有历史测量提示收益上限有限，且已有缓存原型在低复用场景出现长尾退化。此项适合后期处理，不能作为解决严重跳帧的首选，也不能削弱雾效果换取收益。

### 9. 噪声、洞穴和并行生成：优先级 P3，性能潜力大但改造风险高

先在保留数值运算顺序的前提下复用工作区、消除重复 biome/配置查找和已证实的重复计算。原生成器已复用多组噪声数组，并非每次重新分配全部数据。

完整多线程生成不能只给 `generateChunk` 包线程池：`ChunkProviderOTG` 的 RNG、噪声/河流临时状态是实例字段；`ObjectSpawner` 有共享 RNG、填充状态和保存协调；生成阶段还会调用模组洞穴、地表和结构事件。只让 Map 线程安全无法解决这些问题。

可行的后续架构是：不可变配置快照 → 隔离工作区中的纯地形数据计算 → 受控顺序的主线程提交与填充。异步任务应有数量/内存上限、世界代次、取消和卸载处理，并给渲染线程留 CPU 余量。模组回调和真实世界写入默认仍在所属线程。先证明“纯阶段”边界，再谈并行。

跨区块级联生成也需要记录请求链、区块状态和发起模组。简单延迟跨区块 `setBlock` 会改变后续读取和 RNG，可能产生结构缺口。减少重复预览、重复请求、错误的隐式加载值得做；维持生成结果的任务调度改造属于后期架构项目。现有 `PopulationBoundsCheck: false` 不应为了测速随意更改。

## 上游与第三方方案评估

1. **上游有真实可借鉴的进展。** [PR #1020](https://github.com/PG85/OpenTerrainGenerator/pull/1020) 于 2026-07-23 合并 123 个提交到 `1.12-OTG+`，晚于 v9.7。PR 初始说明的“尚未测试”是早期状态，后续评论有测试和修复过程，不能把它当作当前全部改动均未测试。
2. **不建议整体升级作为第一版方案。** 当前分支引入按存档版本选择的 `LayerRNG`，并重写材料、方块设置等路径；这些包含功能/兼容变化。优先从 v9.7 基线逐项回移，并测现有 ICE、RLTweaker、FermiumMixins、EagleMixins 下的净收益。
3. **OTG-Flow 仅作研究参考。** [作者仓库](https://github.com/Brilliafy/OTG-Flow) 显示 2026-11-03 归档，且公告有未确认的下界新区块损坏报告。[项目页](https://www.curseforge.com/minecraft/mc-mods/openterraingenerator-flow-edition) 的性能表使用不同 JVM/伴随模组，不能用于承诺当前 Java 8 整合包收益；其一致性宣传也不能替代本包回归。因此不推荐直接替换现有游戏。

## 建议交付方式

推荐维护独立的 OTG 源码优化分支，保留包名、模组 ID、预设和存档格式；ICE 继续负责渲染与通用优化。短小、独立的候选也可先用现有 ICE 入口验证，源码分支适合维护结构索引、生命周期和执行上下文等较大改动。

实施前先完成可复现基线构建：v9.7 工程仍使用旧 ForgeGradle 2.3、Gradle 4.5 配置及旧仓库地址，构建链需要验证或维护。编译器升级本身不是运行性能收益。保留原有版权/许可证文件，打包时核对内嵌及游戏目录中的 `OTG-Core.jar`，防止核心组件与主体版本错配。

每项能力只能有一个实现负责。用明确的构建标识/能力表对照 ICE 及其他模组补丁，逐项关闭已内置的重叠补丁，同时保留其非重叠功能。不能期待原有字节码形状检测自动处理所有第三方 Mixin；检查实际变换后的类和启动日志是发布前条件。

## 实施与验收顺序

1. **建立当前整合包基线。** 固定种子、路线、视距、预设、JVM 和所有已启用补丁；取得当前版调用链和阶段耗时。旧 OTG 裸跑成绩只能当辅助参考。
2. **第一批原型。** 单点/高度查询、BO4 空间索引、FromImage 条件快路径，分别开关和验证；按真实热点排序实施。随后处理放置上下文、材料查找。
3. **第二批。** 刷怪器稳定排序、冷加载/模板准备、结构序列化。每项保留独立回退。
4. **最后评估并行。** 只有同步优化后仍明显受生成 CPU 限制，才建设隔离的纯计算管线。若主要长帧仍在 GPU 提交/等待，应继续 ICE 渲染工作。

至少覆盖六类场景：已生成区域原地/移动、新区块快速探索、BO4 密集区域、传送和跨维度、大地图重进及保存、多玩家/刷怪器密集场景。预生成测试能测吞吐，但不能代替游玩帧稳定性测试；本包自带 OTG 预生成器已配置禁用，测试驱动需另行明确。

同时报告客户端帧时间 P50/P95/P99、长帧次数及最大值，服务端 MSPT 分位数/TPS，新区块生成与填充耗时、区块/秒、保存停顿、CPU 分配率/GC，以及锁等待和级联请求次数。用重复、交错顺序的 A/B 测试，区分冷文件缓存与热缓存；计时放在阶段入口，不在每个方块上打昂贵探针。不能只降低 tick 内工作量却让区块队列持续积压。

正确性验收比较固定生成顺序下的方块状态、生物群系、光照、TileEntity/NBT、结构记录及重进后的结果；覆盖负坐标、四种旋转、分支、液体/雪、地图边缘、跨区块和存档重载。原生结果可能依赖填充顺序，所以每种测试顺序应分别与原版同序对照。涉及实时刷怪时记录并重放随机输入及玩家状态，规范化无关的时间/UUID 字段。性能测试和正确性测试分开，避免验证工具污染耗时。

达到“旧存档继续生成一致、整包补丁不冲突、吞吐不退化且 P99 改善”的条件后才值得替换游戏使用。当前尚无这套方案的实机性能增幅，不能承诺百分比或完全消除跳帧。
