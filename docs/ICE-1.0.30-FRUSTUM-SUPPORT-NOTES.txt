OptiFine Fully semantics
After disabled short-circuits, narrow all six coordinates to float. For each
corner, evaluate ((px*x + py*y) + pz*z) + pw in that exact order. In planes
0..3 any distance <= 0 rejects. In planes 4..5 all distances <= 0 reject.
NaN <= 0 is false; replacing !(distance <= 0) by distance > 0 is incorrect.

Reduction
Calculate the two rounded products on each axis before selecting extremes.
This also handles reversed endpoints and zero coefficients times infinity.
For planes 0..3 select the minimum non-NaN product (NaN if both are NaN).
For planes 4..5 select the maximum product, propagating either NaN. Evaluate
the original left-associated sum and retain <= 0 as the rejection predicate.
No coordinate sorting, epsilon, double arithmetic, reassociation, FMA,
cross-frame cache, runtime oracle or retained eight-corner method is used.

Why exceptional arithmetic does not need an old-method fallback
For numeric finite intermediates, rounded float addition is monotone. Thus
the selected products give the smallest/largest corner distance. Signed
zeros have identical <= 0 results. Underflow and overflow preserve this order.
For minimum selection, NaN products may be ignored because every corner using
them fails to reject. If a selected minimum sum first becomes NaN from an
infinity cancellation, every non-NaN alternative at that step can only be
+infinity; later additions leave it +infinity or NaN, never <= 0. If an axis
has only NaNs, every corner is NaN. For maximum selection, any NaN product
already guarantees a passing corner. A selected maximum sum <= 0 cannot have
encountered +infinity or NaN: either would remain positive infinity or become
NaN. Its other possible intermediates are finite values or negative infinity,
so no smaller corner can introduce an infinity cancellation/NaN while the
selected maximum remains <= 0. This preserves the two rejection predicates,
without requiring the selected numeric distance itself to equal a NaN-aware
minimum/maximum in every pathological case.

Validation (outside the game)
tools/experiments/frustum-support-build13/FrustumSupportResearch.java exhausts 20,000,000 combinations of product
extremes including infinities, overflow, NaN and signed zero. Its reference
enumerates the eight products; this is an algebra check, not the sole oracle.
NativeFrustumAdapterTest executes the actual captured Fully method in an
isolated generated class. It compares 300,000 random/IEEE boundary cases and
100,000 rounded plane boundary cases against the transformed method. It also
checks disabled/null planes, first-four/last-two difference, unchanged ordinary
RenderLib method bodies, ASM validity and native-only startup registration.
Capture is local optional input; this machine's run must show no skipped tests
in that test class. No test instrumentation is packaged in the optimizer.

Decision: no demonstrated net gain to justify retaining this implementation.
It has been removed from production, including adapter registration and tests;
all evidence and implementation remain frozen. No formal FPS run was performed
for Build13. Do not reintroduce this product-extrema version based solely on
theory or the mixed-input microbenchmark. OptiFine also already caches parent
AABB Fully results per frame; total section frustum calls overstate its work.
This rejects this implementation, not a proof that every support-vertex
implementation is slower. A different candidate needs new measured evidence.
